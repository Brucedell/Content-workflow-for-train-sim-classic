Animation: clips scrubbed by values

Nothing on a TSW locomotive plays over time. Wheels are posed from the simulation's axle angle, doors and levers from a control's value, buffers from physics. That is exactly how TSC's .ia animations work, so your existing keyed actions translate almost one for one. This part gives the rules, the map, and the Animation Blueprint that plays the clips.

1 · Three animation channels

2 · From object keys to a clip: what the add-on bakes

In the master scene a door is an object with rotation keys on frames 0–24. In TSW the door is a bone, and its clip must hold the same motion as pose-bone keys. The add-on samples every frame, computes the object's motion relative to frame 0 in the bone's frame (through any moving parent, so a pantograph's upper arm bakes correctly under its lower arm), and writes location/rotation/scale keys with linear interpolation into an action named after the clip. One action can hold several bones (both pantograph arms share Pantograph_F). Each action is exported as its own FBX with the take named after the clip, so the editor imports Door_L1, not Armature|Scene. tested: the baked pose matched the object's world motion to 1e-4 at every sampled frame, including the child-of-bone case, and the clips survived an FBX round trip.

3 · Wheels and rods: Axles list or one-revolution clip

Two mechanisms exist and Thomas uses both: verified

MechanismHowUse it for
Axles.Entries on the ABPList the axle bones (axle1, axle2…). The parent class rotates them from the matching SimuGraph axle every frame; no clip needed.Diesels, electrics, wagons: plain wheelsets.
Wheels_FullRotation clipA clip holding exactly one revolution of everything that turns with the wheels: wheels, crank pins, rods, pistons. Scrubbed by WheelRotation_DEG / 360.Steam: rods and valve gear; anything geared to the wheels.

The add-on always writes Wheels_FullRotation: if the scene has a clip of that name it is baked from your keys (rods included); otherwise it generates one that turns every axle bone 0→360° about its Y axis over 60 frames, forward roll for +X travel (tested: the wheel top moves +X). Frame 0 and the last frame are identical poses, as the clip must loop. Which local axis the Axles mechanism spins is not documented; the clip route is exact regardless, which is why the guide recommends exporting it anyway. check

4 · Doors, levers, needles, pantographs: VHID clips

Every control-driven part is the same recipe: one clip from closed/zero/lowered at frame 0 to open/full/raised at the last frame, and one entry in the ABP's VirtualHIDSequenceEntries mapping the RVM component name to the clip. The engine evaluates the clip at time = the VHID's output value.

Give each control-driven object a tsw_vhid property with the RVM component name it will be driven by (CabDoor_L, ThrottleControl). The build sheet then lists the VirtualHIDSequenceEntries you have to type: component → clip.

5 · Bogies and buffers: the engine does them

List the bogie bones in Bogies.Entries and the buffer bones in BufferBones. The parent class yaws bogies to follow the track under the body and translates buffer bones by the compression the physics component computes from the buffer stiffness. No clip, no keys. TSC's rule that the XML pivot wins is replaced by the bone position: put the bogie object's origin at the real pivot before exporting. verified (Thomas's lists; bogies empty on a rigid-frame engine).

8 · The Animation Blueprint (RailVehicleAnimInstance)

Every skeletal mesh on the RVV uses an Animation Blueprint whose parent class is RailVehicleAnimInstance, not the plain AnimInstance. The parent adds four lists and a graph node that does the work. Thomas's entire exterior ABP: verified

Parent-class propertyMeaning / Thomas value
Axles.Entries[]Bones the engine spins from axle rotation: axle1, axle2, axle3, axle_Rod_L, axle_Rod_R.
Bogies.Entries[]Bones yawed to follow the track. Empty on Thomas.
BufferBones[]buffer_fl, buffer_fr, buffer_bl, buffer_br.
VirtualHIDSequenceEntries[]Per LOD: {Component (RVM VHID name), Sequence}. CabDoor_L → CabDoor_L.anim, CabDoor_R → CabDoor_R.anim.
CachedModelActorRuntime pointer to the RVM, resolved for you.

The simulation value arrives through a property binding: a variable of the struct type {NodeReference(“Simulation”, “Axle2”), ParameterReference(“WheelRotation_DEG”)} that the parent class evaluates every frame. The build sheet lists the axle names so you know which node to bind.

What the wagon stream adds about the lists

On creating the ABP (parent RailVehicleAnimInstance) the editor auto-filled four Axles entries and two Bogies entries from the bone names. The wheels still did not turn in Play until two more things were set: the ABP's model actor reference (the wagon's RVM class), and, on each Axles and Bogies entry, the simulation component (Simulation) and the SimuGraph node it belongs to (bone Axle1 ↔ node Axle1, bone Bogie1 ↔ node Bogie1). So an entry is “bone + sim node”, not just a bone. After that, wheels and bogies moved with no clip at all. community
